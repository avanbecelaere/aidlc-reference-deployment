# AI-DLC reference deployment

A small, complete, reproducible AWS deployment built by taking a written intent
through the **AI-DLC** workflow, with a human approving each stage.

The thing on display is **the process**. The application is deliberately trivial,
a single containerised HTTP service returning a fixed response, so that nothing
about it competes for attention with the workflow that produced it.

---

## Start here

| Read this | For |
|---|---|
| `docs/vision.md` | What is being built, why it is this small, and what success means. This is the input the AI-DLC run consumes. |
| `docs/running-aidlc-v1.md` | How to run AI-DLC v1 without it silently failing. Read before the first prompt. |
| `docs/prerequisites.md` | The two things created by hand, outside this repository, before any Terraform is applied. |
| `docs/deploy.md` | Deploying through GitHub Actions, reading the service address, tearing down, and troubleshooting. |
| `local-values.template.md` | Copy to `local-values.md` and record your own account, repository and resource names. That filename is gitignored. |
| `aidlc-docs/` | Generated by the run: the stage artifacts, the state pointer, and the approval record in `audit.md`. Absent until the first run. |

If you only read one thing, read `docs/vision.md`.

## Nothing is required from attendees

If you are attending the session this was built for, **you need to bring
nothing**: no backlog item, no repository access, no credentials, no environment,
no preparation. It runs entirely in an AWS account owned by the presenters.

## What is in here

```text
CLAUDE.md                 AI-DLC v1 rules 1.0.1. This file IS the workflow.
.aidlc-rule-details/      The 31 stage detail files the rules load on demand.
docs/                     Vision, prerequisites, deploy runbook, operating procedure.
app/                      Dockerfile and the one static file the service returns.
infra/                    The single Terraform root module, its tests and lock file.
.github/workflows/        pr-checks (no credentials), deploy, destroy, verify-oidc.
aidlc-docs/               Generated by AI-DLC: stage artifacts, state, audit log.
```

**One deliberate departure from `docs/vision.md`.** The vision says the workflow
"plans on a pull request". Here, pull requests run checks only, and they use no
AWS credentials: `fmt`, `validate`, offline `terraform test`, and `docker build`.
The real `terraform plan` runs in the manual deploy workflow, immediately before
apply. The reason is that the hand-made deploy role trusts the `main` branch
only, so a pull-request run cannot assume it. Pull requests from forks get no
OIDC token at all. The decision is recorded in `aidlc-docs/audit.md` and in
`aidlc-docs/inception/requirements/requirements.md` (FR-7).

AI-DLC is **not** a plugin, extension, or tool. It is a markdown rules file read
into the coding agent's context. `CLAUDE.md` is that file, placed where Claude
Code reads project memory. Other agents read it from other locations; see the
[AI-DLC v1 installation guide](https://github.com/awslabs/aidlc-workflows/tree/v1).

This matters more than it sounds. Because the workflow is only text in context, it
can fail to activate while appearing to run, and its approval gates are prose
rather than enforcement. `docs/running-aidlc-v1.md` exists entirely to deal with
those two facts.

## Reproducing it

1. Read `docs/vision.md`.
2. Copy `local-values.template.md` to `local-values.md`, then work through
   `docs/prerequisites.md` against your own AWS account and GitHub
   repository. Nothing in it is created by Terraform, and nothing in it is
   removed by `terraform destroy`.
3. Follow `docs/running-aidlc-v1.md` to start the run, and verify activation
   before continuing.
4. Approve each stage deliberately. The approval record in `aidlc-docs/audit.md`
   is the artifact that makes this reproducible by someone who was not present.

Being reproducible by a stranger is a stated success criterion, not a nicety. It
is also the one that most often fails. If a step here does not work for you, that
is a defect in this repository.

## What this is not

A teaching artifact, not a starting point for production, and it should not be
presented as one. It does not address multi-account separation, secrets
management, network egress control, backup, or compliance posture. The endpoint is
unauthenticated and reachable from a single operator address, which is acceptable
only because it returns a constant and lives in an isolated account for a matter
of hours.

The security governance review this work would normally receive **has not been
run**. Treat the IAM policies and the network rules as drafts, and review them
against your own standards before reusing the pattern.

## Teardown

Tearing this down is part of the exercise, specified in `docs/vision.md` section 8
and `docs/prerequisites.md`. The parts created by hand, the state bucket and the
federated trust relationship, are **not** removed by `terraform destroy` and have
to be deleted deliberately. A deployment role and a trust relationship left behind
in an account that stays in use are a standing access path, long after anyone
remembers why they exist.
